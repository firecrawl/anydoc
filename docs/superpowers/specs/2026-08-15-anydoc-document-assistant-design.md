# AnyDoc 文档理解助手设计规格

日期：2026-08-15  
状态：用户已批准
目标平台：Windows 10/11  
项目目录：`D:\项目保存地址\各应用转md文件应用`

## 1. 产品目标

在 Firecrawl AnyDoc 开源项目及其 WebAssembly Web Demo 基础上，构建一款本地优先的 Windows 文档理解桌面应用。应用读取 Word、PowerPoint、PDF 及 AnyDoc 支持的其他格式，不只输出文字，还结合视觉模型理解页面中的图片、截图、图表、流程图和空间关系，再由文本模型梳理全文、生成摘要并支持带来源页码的连续问答。

产品面向个人使用，也可制作 Windows 安装包交付给同事独立安装。第一版不建设账号、云同步、多人协作、计费、独立向量数据库或知识库管理系统。

## 2. 已确认的技术方向

1. 以官方 `firecrawl/anydoc` 仓库为项目底座，保留上游远程地址以便后续同步。
2. 保留 AnyDoc Rust 解析核心与 WASM 能力，尽量不修改解析器内部实现。
3. 以 `wasm/www/` Web Demo 的交互和视觉语言为界面起点，保留橙色品牌色、拖拽上传和 Markdown 转换体验。
4. 新增独立的文档助手应用模块，避免把模型、存储和桌面业务全部写入 AnyDoc 的单文件 Demo。
5. 使用 Tauri 打包 Windows 桌面应用；前端继续使用 Web 技术，桌面后端负责系统文件、凭据、SQLite、渲染器和任务调度。
6. AnyDoc 使用 MIT 许可证。应用分发时保留 AnyDoc 原始版权声明与许可证文本。

新增应用使用 React、TypeScript 与 Vite 将原始单文件 Demo 重构为可测试模块，同时复用其视觉资产、转换逻辑和交互语言。Tauri 后端使用 Rust；异步任务、HTTP、序列化和 SQLite 分别通过 Tokio、Reqwest、Serde 和 Rusqlite 实现。前端不得直接持有 API Key，也不直接请求模型服务；所有模型请求由 Tauri 后端读取 Windows 凭据后发出，从而规避浏览器 CORS 并降低密钥泄露风险。

建议目录边界：

```text
anydoc/
├─ src/                         # AnyDoc Rust 核心，尽量保持上游一致
├─ wasm/                        # AnyDoc WASM 绑定及原始 Demo
├─ node/ python/ tests/ ...     # 上游原有模块
├─ apps/
│  └─ document-assistant/
│     ├─ src/                   # 模块化前端
│     ├─ src-tauri/             # Windows/Tauri 后端
│     └─ public/                # 继承并扩展 Demo 视觉资产
└─ docs/superpowers/specs/      # 本项目设计规格
```

## 3. 第一版功能范围

### 3.1 文件与本地解析

- 拖拽或文件选择器导入文档。
- 第一版重点验收 `.doc`、`.docx`、`.ppt`、`.pptx`、`.pdf`。
- AnyDoc 其他已支持格式保持可导入，不为每一种格式额外建设专属界面。
- 使用 AnyDoc 生成 Markdown、统一文档结构、表格、列表、脚注、PPT 演讲者备注和嵌入资源。
- 显示解析耗时、文件格式、字符数、页数或幻灯片数。
- 支持复制与下载原始 Markdown。

### 3.2 页面渲染与视觉理解

- 将 Word 页面、PPT 幻灯片和 PDF 页面渲染为图片。
- DOC/DOCX/PPT/PPTX 优先通过本机 Microsoft Office 转为临时 PDF；Office 不可用或转换失败时使用 LibreOffice Headless。
- 安装器将 LibreOffice Headless 作为默认勾选的可选运行组件，并随应用保存相应许可证声明；用户取消该组件且电脑没有可用 Office 时，应用仍能进入纯文本模式。
- PDF 页面统一通过受控的本地 PDF 渲染组件转为 PNG，避免视觉模型面对不同 Office 后端时产生不同输入流程。
- 渲染结果按页缓存。
- 视觉模型逐页分析截图文字、图表、流程图、图片内容和空间关系。
- 每页输出结构化 JSON，包括页码、标题、摘要、视觉元素、关系、关键事实、不确定项和置信度。
- 模型不得猜测看不清的数字；无法确定时写入不确定项。

### 3.3 全文理解

- 文本模型合并 AnyDoc 原文、表格、备注和逐页视觉结果。
- 输出文档主题、章节结构、逻辑脉络、核心观点、关键数据、风险、矛盾点和行动事项。
- 所有可追溯结论关联来源页码或幻灯片编号。
- 支持重新分析全部文档或仅重试失败页面。

### 3.4 连续文档问答

- 支持围绕当前文档连续提问。
- 回答上下文包括 AnyDoc 原始文本、表格与备注、逐页视觉结果、全文摘要、相关页面和最近对话。
- 短文档在模型预算允许时使用完整上下文。
- 长文档使用章节摘要、页级摘要和 SQLite FTS5 全文检索选择相关页面。
- 第一版不依赖独立向量数据库或嵌入模型。
- 回答必须附来源页码；点击页码跳转到原页核对。
- 没有证据时明确返回“文档中未找到相关信息”，不将模型常识伪装成原文。

### 3.5 导出

- 导出 AnyDoc 原始 Markdown。
- 导出包含视觉结果和全文梳理的增强 Markdown。
- 导出结构化 JSON。
- 导出内容保留页码、模型、分析时间和失败页信息。

## 4. 双模型路由

模型适配层使用统一的 OpenAI Compatible 配置，至少支持 Base URL、API Key、模型名称、超时、并发数和连通性测试。

应用支持三种运行模式：

1. 单一多模态模型：同一模型处理页面图片、全文总结和聊天。
2. 视觉模型与文本模型分离：视觉模型逐页分析，文本模型负责长文整合与连续问答；这是推荐模式。
3. 纯文本降级：没有视觉模型时仍使用 AnyDoc 内容完成总结和问答，并清楚标记“视觉内容未分析”。

视觉与文本配置可以复用，也可以完全独立。每个配置保存能力标识，避免把图片发送给不支持视觉输入的模型。

统一内部接口：

```text
analyzePage(pageText, pageImage, nearbyContext) -> PageAnalysis
summarizeDocument(structuredDocument, pageAnalyses) -> DocumentSummary
answerQuestion(documentContext, conversation, question) -> CitedAnswer
```

模型响应首先要求严格 JSON；解析失败时执行一次修复请求，仍失败则保存原始响应并将该步骤标记为可重试失败。

## 5. 用户界面

### 5.1 AnyDoc 增强首页

- 保留 AnyDoc Logo、橙色视觉语言、简介和拖拽区域。
- 顶部新增“文档历史”“模型设置”“关于”。
- 导入完成后显示本地解析、页面渲染、视觉分析和全文梳理的分阶段进度。

### 5.2 结果区域

转换结果使用以下视图：

- 智能解读：全文结论、逻辑脉络、关键数据与来源。
- Markdown：AnyDoc 原始输出与增强输出切换。
- 原页核对：页面或幻灯片图片、页级文本与视觉分析并列显示。
- 文档问答：连续聊天与可点击页码引用。
- 结构化 JSON：展示并导出机器可读结果。

### 5.3 模型设置

- 视觉模型与文本模型分区配置。
- 支持“复用同一配置”。
- 提供 API 连通性测试和视觉能力测试。
- API Key 默认遮挡，不提供明文导出。
- 模型调用前展示隐私提示，说明将发送的文字和页面图片。

## 6. 本地数据与安全

源码保存在指定项目目录。应用运行数据保存在当前 Windows 用户的应用数据目录，例如：

```text
%APPDATA%\AnyDoc Assistant\
├─ app.db
├─ documents\{document-id}\
│  ├─ source-info.json
│  ├─ original.md
│  ├─ pages\
│  ├─ assets\
│  ├─ vision-results.json
│  └─ document-summary.json
└─ logs\
```

- 文档 ID 根据文件哈希生成，用于去重和任务恢复。
- 原文件默认不复制，只保存来源路径、文件哈希和派生缓存。
- 页面图片、解析结果和分析结果保留在缓存中，原文件移动后仍可查看既有分析。
- 删除历史只删除应用缓存，不删除用户原文件。
- SQLite 保存文档元数据、处理状态、页级索引、模型非敏感配置和聊天记录。
- API Key 使用 Windows 凭据库保存，不写入 SQLite、日志或导出文件。
- 日志不得记录 Authorization 请求头、完整 API Key 或原始敏感文档内容。
- 调用云模型是唯一默认离开本机的数据路径；每个模型配置清楚显示这一点。

## 7. 任务状态与恢复

任务阶段：

```text
queued -> parsing -> rendering -> vision_analysis
       -> text_synthesis -> completed
```

每个阶段记录开始时间、完成时间、进度、错误和可重试状态。页面视觉分析以页为最小持久化单位，完成一页立即写入结果，因此应用重启后只处理未完成页面。

用户可以暂停、继续、取消或重试任务。取消任务不删除已完成缓存；重新分析时可选择复用本地解析和渲染结果。

## 8. 异常处理

- 加密文件：提示需要先解除密码保护，不进入模型阶段。
- 损坏或格式不支持：显示 AnyDoc 错误类型和可操作说明。
- AnyDoc 解析失败：保留文件元信息，不生成虚假空结果。
- Office 渲染失败：尝试 LibreOffice；仍失败时允许纯文本模式继续。
- 单页视觉分析失败：不阻塞其他页面，标记失败页并提供重试。
- 视觉模型不可用：降级为纯文本分析并显示醒目标识。
- 文本模型不可用：保留 AnyDoc Markdown 和视觉结果，允许稍后继续全文梳理。
- `401/403`：停止该模型的新请求并提示检查密钥或权限。
- `429`：遵循响应头并指数退避，降低并发。
- `5xx`、超时和断网：有限次数重试，随后进入可恢复失败状态。
- 无效 JSON：执行一次格式修复；仍失败则保存原始响应供诊断。
- 应用异常退出：下次启动从 SQLite 状态和页级结果恢复。

## 9. 性能与资源规则

- AnyDoc WASM 转换在 Web Worker 中执行，避免阻塞界面。
- 页面渲染和模型请求在后台任务执行器中运行。
- 默认模型并发保守设置，可由用户调整，但不超过配置的最大并发。
- 页面图片在满足文字可读性的前提下限制尺寸和质量，避免请求体过大。
- 长文档按页和章节分层汇总，不一次向模型发送所有页面图片。
- 缓存提供按文档删除和清理全部功能，并显示占用空间。

## 10. 测试与验收

### 10.1 测试层级

- 单元测试：文件识别、模型配置、JSON 校验、引用页码、任务状态转换和检索逻辑。
- 集成测试：AnyDoc WASM、Tauri 命令、SQLite、凭据库、Office/LibreOffice 渲染和模型适配器。
- 模型契约测试：使用 Mock Server 覆盖成功、流式、超时、401、429、5xx、无效 JSON 和断网。
- 恢复测试：在解析、渲染、视觉分析和全文梳理阶段强制终止应用，验证重启续跑。
- 打包冒烟测试：在未安装 Node、Rust、Python 的干净 Windows 电脑或虚拟机上安装并运行。

### 10.2 文件矩阵

至少包含：

- 普通与复杂 DOCX。
- 传统 DOC。
- 纯文字、图表、流程图、SmartArt、分组图片和备注型 PPTX。
- 传统 PPT。
- 文本型和图片型 PDF。
- 合并单元格表格、中文字体、长文档、损坏文件和加密文件。

### 10.3 第一版验收标准

1. 支持格式能够在本地输出结构清晰的 Markdown。
2. 页面渲染后，视觉模型能够产生页级图片、图表和关系描述。
3. 文本模型能够合并原文与视觉结果形成全文梳理。
4. 连续问答保留对话上下文并返回可点击来源页码。
5. 没有视觉模型时能够完成纯文本降级流程。
6. 部分页失败不影响其余页面，任务可重试和恢复。
7. Markdown 与 JSON 可以成功导出。
8. API Key 不出现在数据库、日志和导出文件中。
9. Windows 安装包能在无开发环境的电脑上运行。

## 11. 明确不在第一版范围内

- 用户注册、登录和多租户隔离。
- 云端文档同步与多人协作。
- 订阅、计费和用量结算。
- 独立向量数据库、知识库空间和跨文档语义检索。
- macOS、Linux、移动端安装包。
- 在线 Office 编辑器。
- 对任何视觉模型输出准确率作绝对保证。

## 12. 实施顺序约束

实施从获取 AnyDoc 上游源码开始，但先建立独立应用边界和测试框架，再扩展功能。AnyDoc 上游解析核心保持可同步；新增业务功能进入 `apps/document-assistant`。每个里程碑都应保持现有 AnyDoc 测试可运行，并为新模块增加对应验证。
